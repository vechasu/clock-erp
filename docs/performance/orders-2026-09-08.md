# Диагностика и ускорение заказов — 2026-09-08

База исходного кода: `58750c0` (PR #491). До изменения кода выполнены read-only SQL-замеры production и HTTP/browser-профилирование изолированного стенда.

## Методика и границы измерений

Production: Python 3.6.8 / SQLite 3.7.17, **16 471 заказ**, orders.db 44 MiB, catalog.db 220 MiB. SQL открыт через `mode=ro` и `PRAGMA query_only=ON`; payload/персональные данные не выгружались. Production во время диагностики не изменялся.

Для сравнения HTTP до/после использована одна и та же форма синтетических данных: 16 468 WB + 3 Tictactoy, каталог из штатного isolated preview. Это проверка масштаба и критического пути, а не копия распределения production. Python 3.9.6 / SQLite 3.43.2, локальный Flask test client, cProfile, execute/fetchall timing. Внешние API заблокированы. В исходном HTTP-замере Bitrix-detail заменён локальной фикстурой: реальное ожидание Bitrix в цифры **не входит**. На production GET карточек не вызывался, чтобы не запускать прежние фоновые записи/синхронизации.

Таблица — медиана двух тёплых запусков после первого запроса; абсолютные значения включают cProfile. Получение общего COUNT само по себе проблемой не являлось.

## Исправленная модель чтения и индексы

`work_status` — дополнительная производная колонка, исходные `status` и `payload_json` сохраняются. Проекция заполняется при миграции пакетами по 200, далее — в той же транзакции, что и обновление заказа. Для Tictactoy актуальные ERP overrides присоединяются SQL JOIN к локальному каталогу, без загрузки всей таблицы статусов в Python. Правила отображения WB и приоритет ERP статуса не меняются.

| Добавленный индекс | Обоснование |
|---|---|
| idx_orders_page(created_sort, order_id) | Старый created_sort/source_position/order_id не соответствует ORDER BY; устраняет сортировку всей истории |
| idx_orders_source_page(source, created_sort, order_id) | Та же сортировка при WHERE source=? |
| idx_orders_work_status(work_status, source, created_sort, order_id) | Статусный фильтр и узкий покрывающий индекс для счётчиков |
| idx_orders_number(number_fold) | Точный поиск — одна ветвь индексируемого OR |
| idx_orders_external(external_order_id) | Другая ветвь точного OR; существующий source/external_id не покрывал поиск без source |

Индексы заказного PK, продаж и комментариев уже работали; дополнительные для них не добавлялись. Для `%подстрока%` обычный B-tree не поможет: поиск продолжает проверять нормализованные локальные SQL-поля, не десериализуя все заказы в Python. FTS и изменение семантики поиска не вводились.

На **production runtime 3.6.8 / 3.7.17**, в отдельной синтетической БД 16 471 заказ, полный `store.query({})` занял 20.67 мс, source-фильтр 24.18 мс, точный номер 19.61 мс, страница 300 — 22.93 мс. В эти значения входят COUNT, текущая страница и верхние счётчики. Повторное применение миграции успешно, число заказов 16 471. Это отдельная проверка совместимости, не прямое сравнение с production-данными.

Новые планы на SQLite 3.7.17:

```text
page: SCAN TABLE orders_snapshot USING INDEX idx_orders_page
exact number OR id OR external_id:
  SEARCH USING INDEX idx_orders_number
  SEARCH USING INDEX sqlite_autoindex_orders_snapshot_1
  SEARCH USING INDEX idx_orders_external
counts: SCAN USING COVERING INDEX idx_orders_work_status
        USE TEMP B-TREE FOR GROUP BY
```

Временная группировка узких статусов допустима; payload JSON в неё не передаётся. Пагинация остаётся SQL LIMIT/OFFSET. Проверка схемы кэшируется по inode/schema_version/ledger и не повторяет полный аудит данных на каждом открытии.

## N+1, карточки и API

Сопоставления товаров загружаются одним запросом для order_ids текущей страницы. Кандидаты каталога ищутся пакетно с теми же правилами точного совпадения/неоднозначности; затем товары загружаются одним products_by_ids. Идентичные товары разных заказов не вызывают повторных запросов.

Карточка с `X-Order-Detail: 1` не вызывает current_orders_list_state/get_orders/get_order и не готовит товары/продажи/историю соседних заказов. Выбранный заказ, его комментарии, продажа и нужные позиции читаются локально. Полный прямой URL сохраняется; исходное открытие ссылки в новой вкладке по-прежнему возвращает документ со списком. `Vary: X-Order-Detail` разделяет эти представления в HTTP-кэше. Ручные операции продажи/статусов и WB sync endpoints сохранены. Обычный просмотр не запускает Bitrix refresh/backfill/comments sync; явная синхронизация и специально предусмотренный внешний поиск точного отсутствующего номера остаются отдельными действиями. Локальные исправления tracking сохраняются.

| Документ списка | 1 334 | 259 |

Регрессия проверяет одинаковые четыре запроса и строго 20/50/200 JSON-десериализаций при соответствующих размерах страницы; отдельная проверка подтверждает постоянное число запросов обогащения при 20 и 50 заказах. История всех 16k никогда не загружается для просмотра.
