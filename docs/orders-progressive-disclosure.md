# Заказы: рабочий интерфейс и диагностика

Вкладки «Все заказы», TicTacToy и Wildberries используют реальные счётчики ERP. Список показывает товар, фото сопоставленного товара, артикул, дату, количество единиц, сумму, состояние заказа и отдельное состояние продажи. Вторичные сведения раскрываются в строке и карточке; диагностика WB содержит прежние синхронизацию, ошибки, восстановление и импорт поставки.

## Аудит и согласованный приоритет

Read-only аудит сохранённых production-данных 07.09.2026: 14 WB-заказов, у каждого одна позиция и одна единица. `normalize_wildberries_order` задаёт `quantity=1` и `item_units=1`; для TTT `order_item_units` суммирует quantity всех позиций. Поэтому количество подписано «шт.», а число позиций в карточке — отдельно.

TTT загружается клиентом Bitrix в `OrdersSnapshotStore`, WB — существующим адаптером API и восстановлением поставок. Найдены 6 857 TTT-заказов с нерасшифрованными F/P/W и конфликт C («Отказ») в snapshot против assembled в ERP. Максим подтвердил приоритет сохранённого ERP-статуса. Фильтрация, счётчики и подписи теперь используют этот приоритет **до пагинации**. Неизвестные состояния остаются отдельными; исходные значения не перезаписываются.

WB supplierStatus и wbStatus сохраняются отдельно. Например, complete/waiting → «В доставке», complete/sold → «Получен покупателем», ready_for_pickup → «В пункте выдачи»; отмены имеют собственные подписи. Основание: [документация WB](https://dev.wildberries.ru/docs/openapi-other/sandbox-environment). Факт ERP-продажи определяется существующей связью source + external_order_id и не подменяет статус WB.

Поиск номера продолжает обходить статус и период, но соблюдает источник. Текстовый поиск, страница и источник сохраняются в URL; прокрутка — в sessionStorage. Смена источника закрывает чужую карточку. История восстановления строится из сохранённых recovered_at/recovered_from_wb.

## Проверки и ограничения

- 202 теста `test_order*.py`, 62 теста `test_wildberries*.py`, 9 тестов `test_internal_orders.py` — прошли в изолированном runner с заблокированной внешней сетью.
- 15 frontend unit-тестов, typecheck приложения/unit/E2E, ESLint, production build — прошли.
- 6 Playwright-сценариев: источники/поиск, дальняя пагинация/возврат/scroll, карточка/задачи/история, диагностика/импорт, responsive, отправка продажи и запрет повторной отправки. Запуск: `node node_modules/@playwright/test/cli.js test --config playwright.orders.config.ts` из frontend.
- Проверены Python/JS syntax, runtime DDL gate, SQLite compatibility и `git diff --check`.
- Desktop 1440 и mobile 390 просмотрены вручную; также проверена ширина 1024. [Desktop](screenshots/orders-progressive/desktop.png), [Mobile](screenshots/orders-progressive/mobile.png).

Схемы, миграции, синхронизация, проведение продаж, идемпотентность и операции интеграций не переписаны. Новых зависимостей нет. Браузер использует синтетические данные и подменённые ответы записи; реальные продажи, статусы и остатки не менялись. Production не развёрнут по условию задачи. Откат: revert PR; миграций и изменений конфигурации нет.
