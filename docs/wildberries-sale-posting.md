# Проведение заказов Wildberries в ERP

Статус: `current`. Контракт реализации ветки `agent/wb-sale-posting`.
Дата: 2026-09-07. Production в рамках этой задачи не изменяется.

## Найденная архитектура и изменения

1. **Хранение WB.** `normalize_wildberries_order` преобразует сборочное FBS-задание в сохранённый заказ `OrdersSnapshotStore`: внутренний ключ `wb:<id>`, внешний `wb_order_id = id`. Получение и синхронизация заказов не изменены. Текущий нормализатор создаёт одну позицию количества 1 на сборочное задание. `orderUid` и `rid` сохраняются, но не используются для искусственной группировки. Адаптер проведения обрабатывает все позиции сохранённой сущности, если их несколько.
2. **TicTacToy.** Кнопка отправляет POST `/order/<id>/stock-writeoff`. Endpoint проверяет заказ, сопоставляет позиции и вызывает `SalesInventory.create_sale_batch`, либо `create_order_strap_replacement_sale` при замене ремешка. Общий сервис создаёт `erp_sales`, `erp_sale_items`, движения и запись журнала в одной транзакции. Синхронизация статуса Bitrix остаётся только в endpoint TicTacToy.
3. **Файлы.** Добавлены `app/services/wildberries_sales.py` и `tests/test_wildberries_sales.py`; изменены `app/web.py`, `app/templates/orders.html`, `app/templates/sales.html`, `tests/test_wildberries_orders.py`, документация и реестр.
4. **Переиспользование.** Новая система продаж не создана. `WildberriesSales` подготавливает данные и вызывает существующий `SalesInventory`. Из TicTacToy вынесено только чтение полей формы замены ремешка в `order_strap_replacement_form`; поведение TicTacToy сохранено. Resolver сопоставления передаётся адаптеру явно, поэтому будущий фоновый обработчик сможет вызывать тот же сервис.
5. **Сопоставление.** Используется существующая `build_order_product_mapping_context`: явная связь в `erp_order_product_mappings` имеет приоритет; затем точные article/vendorCode, barcode/skus и nmId через `catalog_products.external_source/external_product_id`. Для WB проверяются все штрихкоды и совокупность совпадений: конфликтующие ERP ID блокируют проведение. Нечёткий поиск и автоматическое создание сопоставляемого товара отсутствуют. Ошибка содержит доступный идентификатор WB.
6. **Внешний ID.** Используется исходный `id` сборочного задания WB, а не nmId товара и не идентификатор группы заказов.
7. **Связь с продажей.** `erp_sales.source = wildberries`, `external_order_id = wb_order_id`; в metadata сохраняются номер заказа, время заказа, позиции и WB-идентификаторы. Источник в UI отображается как Wildberries. Тип `automatic` соответствует существующей модели импортированных заказов и не означает автоматическое проведение без сотрудника.
8. **Повторы.** Сервис сначала ищет существующую связь, включая отменённые/удалённые продажи. Общий сервис повторяет проверку внутри `BEGIN IMMEDIATE`, используя стабильный `wildberries-order:<id>`. Существующий UNIQUE-индекс `idx_erp_sales_idempotency` обеспечивает защиту ключа в БД. Повторный клик/запрос/синхронизация или две вкладки не создают вторую продажу и не списывают остаток снова. Отдельный индекс уникальности source+external ID не добавлялся: для данного пути используется уже существующий уникальный ключ. Штатные отмены не разрешают повторное проведение WB этой кнопкой.
9. **Остаток и атомарность.** Общий сервис суммирует количества и проверяет текущие локальные остатки внутри транзакции. Условное обновление `stock >= quantity` не допускает минус; блокировки инвентаризации сохраняются. Продажа, позиции, движения, связь с WB и audit journal коммитятся вместе. Ошибка внутри операции откатывает все изменения. При потере ответа после commit пользователь может безопасно повторить запрос.
10. **Комплектация.** Автоматического BOM-разложения SKU в общем batch-сервисе нет. Существующая ERP поддерживает явную замену ремешка: часы-основа, снимаемый и устанавливаемый ремешки. Та же форма и тот же `create_order_strap_replacement_sale` доступны для WB; списываются фактические компоненты, а клиентская позиция сохраняется. Компоненты по имени товара не угадываются.
11. **Цена.** Используется сохранённое `product.price`, совпадающее с отображением WB. Действующая нормализация выбирает `convertedFinalPrice`, затем `finalPrice`, `convertedPrice`, `price`, делит на 100. Формула не изменена; новые скидки/комиссии/логистика/прибыль не рассчитываются. Клиентские hidden-поля цены WB игнорируются. Отсутствующая/некорректная цена и явно нерублёвая валюта блокируют проведение. Отсутствующий currency code сохраняет предположение существующего интерфейса о рублях.
12. **Комиссия.** Сохраняется допустимое пустое значение `commission = ''`. В WB-форме указано, что комиссия пока неизвестна; вводить выдуманную комиссию не требуется. Общие правила комиссии не изменены.
13. **Тесты.** Новый набор покрывает успешное проведение, source, цену, сопоставление, связь, журнал, остаток, последовательные и конкурентные повторы, повторную синхронизацию, отсутствие/неоднозначность сопоставления, конфликт идентификаторов, второй barcode/nmId, ручную связь, несколько позиций, нехватку остатка, rollback при ошибке журнала, списание компонентов, неверную цену/валюту, отменённую продажу, права, отсутствие заказа, безопасную ошибку HTTP, состояние карточки/очереди после refresh. Рендер HTML и синтаксис встроенного JS проверяются без запуска браузера. Старые тесты WB обновлены с запрета ERP-продажи на разрешённое проведение при сохранении read-only WB API.
14. **Проверки.** Полный локальный backend-набор: 1646 тестов, OK, 15 штатных пропусков; после него добавлены дополнительные целевые тесты. Итоговый WB-набор: 46 тестов, OK. Отдельная регрессия `test_order_*.py`: 144 теста, OK. SQL compatibility static-check, runtime DDL gate, Python compile и `git diff --check` проходят. Полный CI-набор запускается в Draft PR; результаты доступны в checks PR.
15. **Миграция и backup.** Миграция БД и изменение конфигурации не нужны. Перед правками создан архив отслеживаемого кода `/tmp/clock-erp-wb-sale-before.tar` из исходного `dff9a5e`. Разработка велась в отдельной чистой рабочей копии; исходные локальные изменения пользователя сохранены. Все тестовые БД временные; рабочие и production-БД не изменялись и не копировались.
16. **Ограничения и риски.** Реальный WB и production для проверки не использовались. Браузер и визуальная проверка мобильной версии не запускались по инструкции; форма использует существующую адаптивную разметку. Новых автоматических отмен/возвратов, публикации статусов, поставок и стикеров нет. Финансовая аналитика WB и окончательные удержания остаются отдельной задачей. Все исходящие записи WB отсутствуют в новом пути выполнения.

## Пользовательский сценарий

В карточке сохранённого WB-заказа сотрудник нажимает «Провести продажу» и подтверждает существующую форму. POST `/order/wildberries/<wb_order_id>/conduct-sale` работает только с ERP. При успехе JSON-ответ обновляет действие на ссылку «Проведён» и показывает toast без полной перезагрузки. Повторное открытие карточки и список «Собрать заказ» получают связь продажи из SQLite независимо от статуса WB. Без JavaScript используется redirect обратно в карточку.

## Откат кода

До выкладки данных для отката нет. Если код будет развёрнут позднее, откатить код предыдущим commit через штатный release-процесс; уже проведённые продажи сохраняются в существующей схеме. Их отмена выполняется отдельной штатной операцией продажи, а не удалением строк БД.
