# Архитектура Vechasu ERP

Статус: `current` для commit `975ef2572edfbf3568c5fac430d31f9d79af1d23`.

## Current

- Приложение — синхронный Flask-сервис. Объект приложения и большая часть
  маршрутов находятся в `app/web.py`; авторизация подключается Blueprint из
  `app/auth.py`.
- Основной UI серверный: Flask рендерит Jinja-шаблоны из `app/templates/`, а
  поведение страниц дополняют встроенный JavaScript и файлы `app/static/js/`.
- Часть оркестрации уже выделена из `web.py`: каталог — `app/catalog/`, отчёты
  продаж — `app/sales_reporting/`, настройки — `app/system_settings/`; доменные
  операции и интеграционные сценарии находятся в `app/services/`.
- Данные распределены между SQLite (`app/catalog_db.py`, auth store), JSON и
  файлами runtime-каталога `instance/`, а также внешними сущностями Bitrix и
  МойСклад. Единого подтверждённого источника истины для всех сущностей нет.
- JSON API существует для товаров, брендов, категорий, приходов, продаж,
  ремонтов, журнала и настроек. Для части ресурсов параллельно зарегистрированы
  `/api/...` и `/api/v1/...`; единого OpenAPI-контракта в репозитории нет.
- Интеграции реализованы клиентами `app/clients/bitrix*.py` и
  `app/clients/moysklad.py`, а также PHP export endpoint
  `bitrix/catalog-export.php`. Тесты используют fake/mock-клиенты; доступность
  production-интеграций этим документом не подтверждается.

## Реальная роль React

В репозитории есть Vite/TypeScript-проект `frontend/`, lockfile и frontend CI.
Однако текущий `frontend/src` содержит только build marker базовой серверной
раскладки, а не страницы ERP. Маршруты `/app/products`, `/app/sales`,
`/app/receipts`, `/app/repairs`, `/app/journal` и `/app/settings` обслуживаются
Flask/Jinja; общий `/app/<path>` перенаправляет на `/app/products`. Поэтому
React в текущем `origin/main` — вспомогательная build-инфраструктура, а не
действующий application shell или источник поведения страниц.

## Legacy

- `app/web.py` остаётся крупным смешанным модулем HTTP, UI-оркестрации,
  бизнес-правил и работы с хранилищами.
- Несколько поколений URL и обработчиков сосуществуют: Jinja routes, `/app/*`,
  `/api/*`, `/api/v1/*`, Excel-сценарии и интеграционные CLI.
- В шаблонах остаются значительные объёмы page-specific CSS и JavaScript рядом
  с общей системой `themes.css`, `erp-components.css` и shared scripts.
- Runtime-состояние смешивает SQLite, JSON и файлы, а миграции выполняются
  прикладными скриптами и idempotent schema setup без общей migration framework.

## Planned

Документы `full-react-rewrite-*` описывают предложения и исторические этапы.
Они не подтверждают активную программу React/PostgreSQL и не являются текущей
архитектурой. Любое возвращение к этой программе требует нового baseline и
решения владельца.

## Unknown

- фактический commit, версии процессов и конфигурация production;
- полный операционный источник истины по каждой сущности;
- утверждённая целевая архитектура;
- статус off-site backups и проверенных процедур восстановления.

## Основной архитектурный долг

1. Концентрация ответственности в `app/web.py` и page templates.
2. Смешанное владение данными и отсутствие единого versioned migration слоя.
3. Дублирующиеся поколения API и маршрутов без опубликованного контракта.
4. Смешение общих UI-примитивов с локальными CSS/JS-реализациями страниц.
5. Исторические документы с точными counts и line references быстро устаревают.
6. Routes `/overview`, `/orders` и `/analytics` рендерят отсутствующие в
   текущем Git templates; соответствующий UI имеет неподтверждённую
   работоспособность.
