# Восстановление пропущенных WB FBS-заказов

Статус: `current` для реализации ветки `agent/wb-supply-recovery`, 07.09.2026.
Статус кода не означает выполненные production deploy или импорт.

## Причина и существующая архитектура

Обычная синхронизация `synchronize_wildberries_orders` использовала только
GET `/api/v3/orders/new`. Перенос задания в поставку убирает его из этого набора.
Существующий клиент уже читал список поставок, но не их состав и историю заказов.
Нормализатор хранит исходный WB `id` как `wb_order_id`, а `OrdersSnapshotStore`
использует канонический `wb:<id>` и пару `wildberries/external_order_id`.
Товар определяется существующим точным сопоставлением по статье продавца,
barcode/skus, nmId либо явной связи `erp_order_product_mappings`.

## Реализация

- Клиент читает метаданные поставки GET `/api/v3/supplies/{id}`, её `orderIds`
  GET `/api/marketplace/v3/supplies/{id}/order-ids`, заказы за период GET
  `/api/v3/orders` с проверенной пагинацией и текущие статусы через специальный
  read-only POST `/api/v3/orders/status` (до 100 ID). Это чтение, не перевод статуса.
  Общий публичный `request_json` остаётся GET-only; POST/PATCH/DELETE операций
  изменения WB не доступны. Официальный контракт:
  [WB FBS API](https://dev.wildberries.ru/en/docs/openapi/orders-fbs).
- `WildberriesRecovery.preview_supply` открывает обе БД только `mode=ro`;
  не импортирует Flask web, не выполняет инициализацию схемы, миграции, продажи
  или списания. Проверяет существующие заказы, любые связанные продажи,
  точные ERP-совпадения, текущий остаток, наличие исходной даты/цены/статуса.
  Неоднозначность не разрешается угадыванием. Исходные доступные поля WB
  сохранены в `wb_raw`, дополнительно есть `wb_supply_id`.
- Классификации: READY, ALREADY_IMPORTED, ALREADY_SOLD, PRODUCT_NOT_FOUND,
  AMBIGUOUS_PRODUCT, NO_STOCK, API_ERROR. Нулевой остаток и отсутствие matching
  не препятствуют сохранению проблемного заказа. Уже существующие заказы и
  продажи пропускаются. Ошибки API оставляют строки в отчёте.
- Для первичной поставки `WB-GI-275015200` обязательно ровно 8 ID; иначе STOP.
  Ручной импорт любой поставки требует свежего подписанного dry-run, действующего
  30 минут. Перед записью WB и matching читаются заново, состав и существенные
  поля сравниваются с подтверждённым результатом. CLI намеренно не имеет `--apply`.
- Импорт вызывает существующий `OrdersSnapshotStore.upsert_wildberries` с
  `only_missing=True`. Один заказ и одно событие существующего `AuditJournal`
  записываются в одной транзакции с attached catalog DB. Проверка продажи
  выполняется повторно под блокировкой. Ошибка одного заказа откатывает его,
  остальные безопасные заказы могут сохраниться. Повторные и конкурентные
  запуски не создают дополнительные заказы или события.
- Метки `recovered_from_wb`, `recovered_at`, `recovery_supply_id` и текст
  `recovery_notice` сохраняются в JSON заказа и переживают обычный sync.
  Исходная дата заказа не заменяется временем восстановления. Событие журнала
  привязано к order `wb:<id>`, источник `wildberries`.
- Кнопка «Обновить WB» сначала выполняет прежний sync новых заказов, затем
  reconciliation за 14 дней: заказы, актуальные поставки и их членство.
  Импортирует только отсутствующие записи. API-ошибки не отменяют уже сохранённые
  новые заказы. Недостающие детали остаются в durable diagnostics/pending и
  повторно проверяются; проблемные товары сохраняются с `requires_matching`.
- Диагностика хранится в существующей `orders_snapshot_meta`, без новой схемы.
  Один общий компонент показывается в WB-карточке/фильтре и «Собрать заказ»:
  время последнего успешного sync, новые, восстановленные, требующие внимания,
  расхождение состава поставок, поле ID, dry-run-таблица и отдельный импорт.
  «Восстановить» запускает проверку, а не продажу. В recovery-инструменте нет
  кнопки проведения продажи.

## Проверки и ограничения

Локальные проверки: WB — 61 тест; существующие заказы — 144; snapshot — 24.
Проверяются dry-run без изменений байтов БД, 8 записей поставки вне `/new`,
повторы, конкурентный импорт, наличие продажи, matching/ambiguity/no-stock,
частичные статусы, неверное количество, rollback журнала, обычный sync,
неизменность TicTacToy, HTTP-подтверждение и пагинация.
Дополнительно: Python compile, `node --check`, SQL compatibility static-check,
runtime DDL gate и `git diff --check`. Результаты обязательного CI — в PR.
Браузер вручную не запускался; используются существующие компоненты интерфейса.

Миграции и новые зависимости не нужны. Перед будущей выкладкой/первым реальным
импортом необходим штатный backup production-БД и проверка схемы. Код до правок
сохранён в `/tmp/clock-erp-wb-recovery-before.tar`. Рабочая копия пользователя
с незакоммиченными правками не изменялась.

Превью по умолчанию смотрит 14 дней; CLI поддерживает `--days 1..30` согласно
ограничению API на один временной интервал. ID из состава поставки без деталей
не превращаются в выдуманный заказ: остаются API_ERROR/pending. Это требует
восстановления доступности API или ручного расширения периода.
Число заказов и текущие остатки могут измениться после dry-run — повторная
проверка перед импортом обязательна. В этом задании production не развёртывается,
первый запуск — только dry-run; импорт ожидает отдельного подтверждения Максима.
Сырые production-ответы и таблица результатов хранятся локально вне Git.
