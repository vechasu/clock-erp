# Рабочая очередь ремонта

Backend-статусы, JSON schema v4, связи и журнал событий сохранены. Новая
`repair_workflow` — чистая функция, общая для карточки, списка и проверки действий.
Она не записывает данные. `/api/v1/repairs` сохраняет прежнюю семантику `view`;
страница `/app/repairs` дополнительно показывает завершённые/отменённые в архивной
вкладке, не заполняя `archived_at` и не перемещая записи в хранилище.

## Аудит

Хранилище — `instance/repair_cases.json`; атомарная запись под `flock`.
`apply_repair_action` проверяет этап, обязательные бизнес-поля и idempotency key,
записывает статус, местонахождение, `updated_at`, `updated_by` и историю изменений.
`control_date` — дата следующей проверки, `waiting_for` — сторона ожидания,
`next_action` — сохранённое пояснение. Просрочка — отдельный сигнал, не этап.
Контакты, идентификаторы заказа/позиции/товара и снимки названий сохраняются.
Создание требует клиента, контакта, товара, проблемы и параметров контроля;
для собственного заказа необходима конкретная позиция. Для повторного — родитель.

Read-only аудит production 07.09.2026: 15 ремонтов, 12 явно архивированы;
активные — две записи `new + at_us`, одна `new + delivered`. В архиве есть
`waiting_payment + outbound_transit` и `new + unknown`. Ни одна запись не исправлялась.
Известные legacy-алиасы нормализует прежний загрузчик. Неизвестный прежний статус,
отмеченный в migration review notes, блокирует предлагаемые переходы.

## State/action mapping

| Backend | Допустимое место | UX | Основное действие |
|---|---|---|---|
| new | with_customer | Новый | Согласовать отправку клиента |
| new | at_us | Нужно действие | Передать мастеру: атомарно receive → start_diagnostics |
| waiting_customer_shipment | with_customer | Ждём отправку клиента | Клиент отправил товар |
| inbound_transit | inbound_transit | В пути к нам | Принять товар после получения |
| waiting_diagnostics | at_us | Нужно передать мастеру | Передать мастеру |
| diagnostics | with_master | На диагностике у мастера | Получить результат диагностики |
| waiting_decision | at_us / with_master | Ждём решения клиента | Зафиксировать решение |
| waiting_payment | at_us / with_master | Ждём оплаты клиента | Зафиксировать оплату |
| in_repair | at_us / with_master | В ремонте | Получили готовый товар |
| ready_return | at_us | Готов к возврату | Оформить возврат; при pickup/other — подтвердить выдачу |
| outbound_transit | outbound_transit | В пути к клиенту | Подтвердить получение |
| completed | delivered | Завершён | Нет; возобновление отдельно |
| cancelled | любое | Отменён | Нет; возобновление отдельно |
| неизвестное / противоречивое | любое | Требует уточнения | Карточка, без перехода |
| archived_at задан | любое | Сохранённый этап / уточнение | Только просмотр |

Местонахождение не вычисляется из цвета. `accept_paid`, `accept_free`,
`record_payment` сохраняют место по существующим правилам, поэтому `at_us` и
`with_master` допустимы на соответствующих этапах. Отсутствие клиента/заказа не
меняет физический этап и не вызывает ошибку отображения.

## Переходы и запись

| Действие | Целевой статус | Изменяемое место | Дополнительные данные |
|---|---|---|---|
| request_shipment | waiting_customer_shipment | with_customer | — |
| mark_customer_sent | inbound_transit | inbound_transit | — |
| receive | waiting_diagnostics | at_us | — |
| start_diagnostics | diagnostics | with_master | — |
| finish_diagnostics / request_decision | waiting_decision | сохраняется | Результат диагностики, решение мастера |
| accept_paid | waiting_payment | сохраняется | Решение клиента, стоимость |
| accept_free | in_repair | сохраняется | Решение клиента |
| start_repair | in_repair | with_master | Существующее альтернативное действие |
| record_payment | in_repair | сохраняется | Сумма, время оплаты |
| mark_ready | ready_return | at_us | — |
| send_to_customer | outbound_transit | outbound_transit | Способ возврата, накладная для cdek/courier |
| complete | completed | delivered | Результат, время завершения; pickup/other при выдаче у нас |
| cancel | cancelled | сохраняется | Причина, время отмены |
| reopen | new или выбранный активный статус | сохраняется | Причина; очистка полей завершения |
| add_incoming_waybill | сохраняется | сохраняется | Входящая накладная |

Все нетерминальные действия по-прежнему требуют контрольную дату. В управляемой
форме (`guided=true`) сервер заполняет пояснение следующего этапа и сторону
ожидания, сотрудник указывает дату. Платный/бесплатный ремонт и способ возврата
сотрудник выбирает явно. Никаких отправок сообщений кнопки ремонта не выполняют.
История записывается существующим механизмом; повторный GET читает сохранённые
значения. Неизвестная комбинация статуса/места отклоняется и через прямой action API.

## Проверки и ограничения

- `python3 scripts/run_backend_tests.py --pattern 'test_repair*.py'`: mapping,
  архив, создание/редактирование, циклы, история, связи, поиск и пагинация.
- `test_stage2_repairs_api.py`: совместимость API.
- `playwright.repairs.config.ts`: 1440/768/390 px, неизвестные/архивные записи,
  полный бесплатный ремонт до самовывоза, refresh/GET/history, создание/редактирование.
- Новый browser regression включён в обязательный frontend CI.
- Полный backend и frontend CI необходимы перед merge.

Миграции и новые зависимости не нужны. Сроки не выводятся из предположений о SLA.
Ложный progress по неизвестным legacy-данным не рисуется. Ручное уточнение данных
сохраняет прежнюю форму; массового изменения статусов нет. Откат — предыдущий
commit штатным deploy с backup, без отката пользовательских данных.

## Второй UX-проход

По умолчанию список содержит только «Статус / Клиент и заказ / Товар / Проблема / Сейчас / Что делать».
Настройки столбцов версии v3 начинают с шести колонок; дополнительные колонки можно вернуть вручную.
Пустые вспомогательные очереди скрыты, основные «Все / Нужно действие / У мастера / Ждём клиента» доступны всегда.

Новый UI создания передаёт `guided_create=true`: клиент/контакт, товар, проблема и одно из двух мест.
Сервер задаёт `waiting_for=us`, пояснение следующего шага, дату проверки на завтра (если не выбрана другая)
и тип «Диагностика» по умолчанию. Выбор «У нас» при создании подтверждает приём и задаёт существующий
статус `waiting_diagnostics`; выбор «У клиента» оставляет `new`. Это явно объяснено под формой.
Прежний POST без флага и PATCH редактирования сохраняют прежнее поведение. Скрытые поля не удалены.

Для существующего `new + at_us` CTA `receive_and_start_diagnostics` выполняет два прежних перехода
на копии записи и публикует результат только после успеха обоих. В истории остаются оба перехода,
повторный idempotency key не дублирует действие. Архив, другое место и противоречивые legacy-состояния
не допускают этот CTA. Просмотр ничего не записывает.

Дополнительные проверки: минимальное создание без открытия secondary-полей, default columns со старыми
настройками, desktop 1440×768 без прокрутки формы, 390 px без горизонтального переполнения,
однокнопочная передача старого ремонта и сохранение обеих записей истории после refresh.
