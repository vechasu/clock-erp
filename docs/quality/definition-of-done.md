# Definition of Done

Статус: `current` как правило проверки изменений; набор конкретных команд
выбирается по затронутой области.

Изменение готово к review, когда выполнены применимые пункты ниже и результат
зафиксирован в Pull Request. Наличие пункта здесь не означает, что для него уже
есть автоматический тест в репозитории.

## Обязательный минимум

- diff ограничен задачей; нет случайных изменений кода, данных, generated
  assets, конфигурации или пользовательских файлов;
- изучены относящиеся к задаче current-документы, а изменённый подтверждённый
  контракт отражён в документации и реестре;
- выполнены `git diff --check`, проверка синтаксиса изменённых файлов и
  целевые тесты затронутого поведения;
- полный diff просмотрен перед commit; секреты, `.env`, production-данные,
  персональные данные, базы и пользовательские загрузки отсутствуют;
- в PR перечислены выполненные и невыполненные проверки, риски, миграции,
  конфигурация и способ отката.

## Если изменён код

1. Запустить узкие unit/service/API tests, прямо покрывающие изменение.
2. Запустить соседние regression tests, когда меняется общий сервис, маршрут,
   шаблон, CSS/JavaScript-компонент или формат данных.
3. Проверить Python syntax/compile для затронутых модулей; для frontend доступны
   `pnpm run typecheck`, `pnpm run lint`, `pnpm run test` и `pnpm run build`.
4. Полную regression запускать при широком контрактном или инфраструктурном
   изменении либо когда targeted coverage недостаточно. Документационный diff
   без кода сам по себе полной regression не требует.

## UI и UX

- выполнить browser smoke затронутого основного сценария и негативного состояния;
- проверить console errors и относящиеся к запросу server logs;
- проверить desktop и mobile layout, клавиатурный focus и доступность основных
  controls; дополнительные темы — если менялись theme tokens или shared CSS;
- проверить loading, empty, validation/error и success feedback;
- для destructive action проверить confirmation, server rejection и отсутствие
  двойной отправки;
- использовать существующие browser tests только там, где они найдены:
  например `test_catalog_combobox_browser.py`, `test_registration_browser.py`,
  `test_receipt_card_browser.py`, `test_warehouse_photo_preview_browser.py`;
  если подходящего теста нет, явно записать ручной smoke.

## Производительность

Если затронуты товары, продажи, приходы, настройки, общий list query или
pagination, сравнить релевантный сценарий до/после. В репозитории есть
`scripts/benchmark_mvp_performance.py` и performance/stage tests, но их область
нужно сверять с изменением; отсутствие ухудшения нельзя заявлять без замера.

## Данные, миграции и rollback

- сначала dry-run на временной копии или test database;
- проверить counts, ограничения, ссылки и бизнес-инварианты до/после;
- для apply-сценария определить backup, restore и критерий остановки;
- повторный запуск должен быть безопасен либо явно запрещён guard-условием;
- реальные Bitrix/МойСклад и production не использовать в тестах записи без
  отдельного разрешения;
- в PR указать, нужна ли миграция, и дать проверяемый rollback.

## Перед публикацией

- ветка основана на актуальном `origin/main`, обязательные проверки зелёные;
- staged diff содержит только файлы задачи;
- документация не называет planned/pending работу внедрённой;
- PR остаётся Draft или ready согласно действующему процессу владельца; merge и
  deploy выполняются только в рамках отдельно разрешённого процесса.

`.github/pull_request_template.md`, [главная документация](../README.md).
