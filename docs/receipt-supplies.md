# Локальные поставки ERP

## Решение и архитектура

Bitrix используется только для выбора/сопоставления карточек. Новые карточки поставки создаются с нулевым остатком, существующие карточки сохраняют свой остаток и поля. МойСклад исключён из активных HTTP-путей прихода и Excel.

Переиспользованы `erp_receipts`, `erp_receipt_items`, `catalog_stock_movements`, `catalog_excel_products` и транзакции `CatalogDatabase.transaction()` (`BEGIN IMMEDIATE`). Новых таблиц и второго журнала нет. Поставка отличается структурированным `metadata_json.source_type=supply`; там же хранятся название, автор создания, автор/время проведения и исторические подписи карточек. Фактические остатки и связи с документом/строкой находятся в существующем ledger.

Новая схема БД не требуется, поэтому DDL-миграции и изменение существующих миграционных checksum отсутствуют. История не переписывается. Старые Excel-операции и JSON-приходы отображаются read-only; для истории без известных остатков показано «—», связи не выдумываются. Проведённые поставки не редактируются/не удаляются. Удаление черновика сохраняет документ со статусом cancelled, не меняя stock и карточки.

Создание, редактирование и удаление черновика не меняют остатки. При проведении заново проверяются строки и актуальные товары; общая транзакция обеспечивает атомарность вместе с продажами. Повторное проведение возвращает существующий результат без нового начисления. Дубли товара запрещены сервером внутри той же транзакции. Общий механизм блокировок инвентаризации сохранён.

Excel создаёт тот же локальный черновик. Используется существующий парсер и точный matcher по локальному нормализованному каталогу Bitrix. Неоднозначная/отсутствующая связь блокирует импорт с указанием строки; сотрудник может уточнить Bitrix ID в файле или заполнить поставку через поиск Bitrix. Импорт не проводит поставку автоматически. Сохранённые черновики проводятся без внешних API.

## Активные пути

- `/app/receipts`, `/receipts`: три вкладки, read-only журнал, список документов, отмены продаж.
- `/api/v1/receipts/supplies`: создание и список поставок.
- `/api/v1/receipts/supplies/<id>`: просмотр, изменение/удаление черновика.
- `/api/v1/receipts/supplies/<id>/post`: проведение.
- `/api/v1/receipts/bitrix`: поиск карточек без поля stock Bitrix.
- `/api/v1/receipts/bitrix/<id>`: локальная карточка из проверенного Bitrix-ответа.
- `/api/v1/receipts/excel`: файл → черновик.
- `/api/v1/receipts/movements`: read-only журнал положительных движений и доступной старой истории.

Старые write endpoints `/receipts/create`, `/receipts/update`, `/receipts/delete`, `/receipts/catalog/create`, `/receipts/import/preview`, POST/PATCH/DELETE `/api[/v1]/receipts` и проведение старого Excel-черновика возвращают 410. Старый код оставлен для исторического контекста, но отключён регистрацией view-функций. `/products/receipts/preview` направлен в новый Excel-импорт. Исторические read API сохранены для совместимости. Старые непроведённые Excel-файлы нужно загрузить в новую поставку.

Существующая авторизация и CSRF сохранены; роли только для чтения дополнительно не допускаются к операциям поставки. В тестах внешние клиенты подменены, все БД временные.

## Остальные места использования МойСклад (вне задачи)

Не удалены и не изменены:

- `app/web.py`: legacy загрузка складского каталога/остатков (`get_warehouse_items`, повторная legacy загрузка warehouse); fallback галереи и миниатюр; отправка складской ячейки; legacy редактирование/архивирование карточки; складские корректировки/списания; сопоставление каталога; fallback изменения фотографий товаров.
- `app/services/moysklad_catalog_mapping.py`: сопоставление ERP/МойСклад.
- `app/clients/moysklad.py`: общий клиент внешнего API.
- `app/services/catalog_reader.py`, `shared_catalog.py`, `excel_product_catalog.py`, `product_reconciliation.py`, `product_excel_export.py`: legacy идентификаторы, состояние сопоставления, экспорт.
- `app/services/receipt_recovery.py`, `brand_inventory.py`, `inventory_lock.py`, `sales_inventory.py`: ссылки/защиты для исторических документов и товаров; наличие этих ссылок не означает новый внешний вызов при поставке.
- Скрипты импорта/сопоставления каталога остаются отдельными административными инструментами.

## Проверки и изменение тестового контракта

Новый `tests/test_supplies.py` проверяет транзакции, отказ одной строки, double-post, конкурентную продажу, идентификаторы, игнорирование Bitrix stock, неизменяемую историю, Excel, отмену продажи, права и CSRF. Старые тесты ручного создания карточки/фото через приход и удалённого документа заменены проверками отключённых write endpoints и локального lifecycle. Продуктовые, продажные и каталоговые части интеграционных тестов сохранены.

`frontend/e2e-supplies` проверяет реальную локальную поставку с двумя товарами, read-only после проведения, журнал/отмену №21096, дубли, валидацию, поиск/пагинацию и ширины 1440/1024/768/390/320. Он включён в CI. Старые встроенные DOM-пробы прежнего редактора заменены этим сценарием, пробы остальных страниц сохранены.

Полный backend-набор после обновления контрактов: 1668 тестов, OK, 14 штатных skips. Финальные локальные/CI результаты указаны в PR. SQL compatibility/runtime DDL checks, frontend typechecks/lint/unit/build обязательны.

## Откат

До выкладки — штатный preflight и backup через `scripts/deploy.sh`; production-настройки не копируются из локальной среды. При откате кода новые движения/остатки не откатывать повторно: проведённые поставки являются совершёнными складскими операциями. После появления новых поставок предпочтителен исправляющий релиз: предыдущий UI не знает метаданных supply. Полное восстановление pre-deploy backup допустимо только с остановленным сервисом и отдельным решением об учёте всех операций после backup.
