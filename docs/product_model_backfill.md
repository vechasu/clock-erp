# Массовое заполнение моделей товаров

## Архитектура и источники

Рабочие карточки ERP находятся в SQLite-таблице `catalog_excel_products`.
Бренды и категории нормализованы в `erp_brands` и `erp_categories`. До этой
задачи модель хранилась только свободным текстом в `catalog_excel_products.model`;
`model_id` и отдельного справочника моделей не было.

Синхронизация Bitrix хранит исходные товары в `catalog_products`, свойства в
`catalog_properties`/`catalog_product_property_values`, варианты в
`catalog_offers`, а затем переносит обогащение в рабочую карточку: название,
артикул/SKU, XML ID, URL, бренд, категорию и JSON свойств. В read-only выгрузке
на 21 августа 2026 года доступно 1484 товара и 56 свойств на товар. Отдельного
заполненного свойства модели нет. `BRAND_MODEL` («Марка часов») содержит бренд и
намеренно исключён из распознавания модели.

## Безопасная схема

Добавлен справочник `erp_models` с уникальностью по `(brand_id,
normalized_name)` и внешний ключ `catalog_excel_products.model_id`. Ключ модели
не зависит от регистра и пробелов, поэтому `BC03`, `bc03` и `BC 03` ссылаются
на одну запись, но дефисы и другие смысловые символы автоматически не
схлопываются. Текстовое поле `model` сохранено для полной обратной совместимости
с карточками, экспортом, ремонтами и поиском.

Приоритет распознавания: явное свойство модели Bitrix, brand-specific правило
по SKU/артикулу, название, URL. Запись разрешена только для `high`; `medium` и
`low` остаются в `manual_review`. Заполненные модели не перезаписываются, а
расхождения попадают в `conflicts`.

Правила сформированы по фактической выгрузке. В частности: Braun отбрасывает
цветовой хвост у BC/BN/BNC; Void сохраняет семейства V03D/V03B/PKG01; Klokers
группирует KLOK-01/KLOK-08; CIGA использует Z062/X011; TID — No.1/No.3/No.4;
именованные семейства Ziiiro, Aark, Eone и ряда других брендов становятся
`high` только при повторении минимум у двух вариантов и подтверждении названием
и ещё одним источником. Ремешки и аксессуары исключены из автоматических
часовых правил. Для остальных брендов код без отдельного доказанного правила
остаётся `medium`, даже если встречается в нескольких полях.

## Dry-run на актуальной read-only выгрузке Bitrix

Проверено 1484 товара. После консервативного ужесточения правил 484 товара
определяются с высокой уверенностью; остальные 1000 требуют ручной проверки.
Конфликтов с существующими ERP-моделями в Bitrix-снимке нет, поскольку снимок
не содержит локальных значений ERP. Окончательные числа production формируются
командой непосредственно перед применением.

Примеры разных брендов: Aark Classic → `Classic`; BENLYDESIGN Mobius X5000
Black → `X5000`; Braun BN0021 Black Brushed → `BN0021`; CIGA Z062-BLGO-W5BK →
`Z062`; Contempus Du Neĝo → `Du`; D1 Milano ATBJ01 → `ATBJ01`; Daniel
Wellington 0506DW → `0506DW`; Eone Bradley Black → `Bradley`; Humism Kato →
`Kato`; Klokers KLOK-01 yellow black → `KLOK-01`.

## Запуск

Dry-run без изменения данных:

```bash
python3 scripts/backfill_product_models.py --output outputs/product-models-dry-run.json
```

Применение только `high` после проверки отчёта:

```bash
python3 scripts/backfill_product_models.py \
  --apply --confirm-high-confidence \
  --output outputs/product-models-applied.json
```

Перед любой записью команда проверяет отсутствие активной инвентаризации и
создаёт согласованный SQLite backup. Все изменения выполняются одной
транзакцией; ошибка откатывает модели, связи и аудит целиком. Аудит содержит
старое и новое значение, источник, правило, уверенность и UTC-время. Повторный
запуск идемпотентен.
