# Документация Vechasu ERP

Этот каталог — единая точка входа в знания о Vechasu ERP. На первом этапе он
не заменяет существующие документы: реестр ниже отделяет подтверждённое
состояние системы от исторических снимков и планов.

## Статусы документов

- `current` — содержание подтверждено актуальным кодом `origin/main`.
- `draft` — предложение или незавершённая реализация.
- `deprecated` — документ описывает больше не используемый подход.
- `archive` — исторический снимок, отчёт или завершённая работа.
- `unknown` — актуальность ещё не установлена.

Статус относится ко всему документу. Отдельные факты внутри исторического
документа могут оставаться верными, но перед использованием их нужно повторно
сверить с кодом.

появятся вместе с первым полезным документом.

Полный перечень документов, их назначение и рекомендуемое будущее расположение
находятся в [реестре документации](document-register.md).

## Как добавлять документ

1. Выбрать раздел по назначению знания, а не по имени команды или файла кода.
2. Использовать один из [четырёх шаблонов](templates/), если он подходит.
3. Указать статус и границы документа; для проверенного состояния привести
   воспроизводимое подтверждение кодом или безопасной проверкой.
4. Не добавлять секреты, production-данные, персональные данные и локальные
   абсолютные пути к пользовательским файлам.
5. Добавить документ в `docs/document-register.md` и связать его с соседними
   документами относительными ссылками.
6. Проверить внутренние ссылки и явно отметить сведения, которые не удалось
   подтвердить.

## Текущее состояние и планы

Текущее состояние и будущий план нельзя смешивать без явных заголовков.
Утверждение о текущем поведении получает статус `current` только после сверки с
актуальным `origin/main`. Предложение помечается `draft` и не становится
стандартом, пока владелец не подтвердит его. Исторические результаты сохраняют
дату и baseline и получают статус `archive`.

## Выявленные пробелы

- создана первая карта продукта, но нет утверждённых владельцем границ модулей;
- нет карты сквозных процессов заказ → склад → продажа/возврат и приход → остаток;
- создана первая карта архитектуры, но нет утверждённого data ownership;
- нет единого актуального справочника API;
- фактические design/UX-паттерны описаны, но нет утверждённого нормативного стандарта;
- нет централизованной модели безопасности и матрицы ролей;
- есть Definition of Done, но нет полной карты покрытия и тестовой стратегии;
- нет отдельного проверенного runbook для deploy, backup и восстановления;
- нет подтверждённых ADR;
- неизвестно, какой commit фактически работает в production: production не
  проверялся, поскольку SSH и deploy не разрешены этой задачей.

## Требуют проверки владельцем

- действующий порядок commit, PR, merge и deploy: `AGENTS.md` и
  `docs/agent-pipeline.md` противоречат друг другу;
- являются ли перечисленные в [`decisions/README.md`](decisions/README.md)
  кандидаты реальными решениями;
- какие production-отчёты допустимо хранить в репозитории и когда они должны
  перейти в архив;
- является ли React-программа активной: текущий `origin/main` не содержит
  описанного в старых отчётах набора React feature-модулей;
- нужен ли отдельный privacy-review исторических отчётов и скриншотов.

## Следующий этап

После решения владельца можно отдельным изменением переместить документы в
рекомендуемые разделы, исправить ссылки и добавить актуальные обзорные
документы. На этом этапе существующие файлы не перемещались и не удалялись.
