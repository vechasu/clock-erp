# Локальные сборные SKU: аудит до реализации

База задачи: origin/main b0bb40a; исходные 123 теста продаж проходят через
scripts/run_backend_tests.py (внешние соединения запрещены). Основная рабочая
папка содержит чужие изменения, задача изолирована в agent/local-sku-bundles.

## Карта существующего учёта

- catalog_excel_products — локальная карточка и физический stock; Bitrix-ссылка
  nullable. ExcelProductCatalog.create_product уже создаёт локальные товары.
- BitrixERPProductSync обновляет перечисленные поля карточки; существующий stock
  не заменяется. Начальный stock импортируется только при создании карточки.
- Удаление локального товара — active=0 с сохранением идентификатора, остатка и
  истории. Отсутствие карточки в очередном импорте не является удалением ERP.
- SalesInventory.create_sale/create_sale_batch списывают stock в BEGIN IMMEDIATE;
  повторная операция определяется по sale ID/idempotency key/внешнему заказу.
- erp_sale_items — коммерческие позиции и аналитика. catalog_stock_movements —
  реальные физические движения; отмена использует их суммарный эффект.
- ReceiptInventory, ручные корректировки ExcelProductCatalog и InventoryControl
  работают с тем же физическим stock. Инвентаризация блокирует товары через
  assert_products_unlocked. Отдельную систему резервирования задача не вводит.
- stock также читают SharedCatalog (фильтры, сортировка, агрегаты), warehouse,
  API товаров, подбор товара продажи, отчёты, закупки, ремонты и Excel-импорт.
  Подмена stock расчётной доступностью меняла бы смысл всех этих потребителей.
- UI товаров: warehouse.html, карточка в editDrawer; API /api/v1/products.
- Схема изменяется только deploy-time runner schema_migrations; runtime DDL
  запрещён. Требуется совместимость SQLite 3.7.17 / Python 3.6.

## Выбранное решение

Новые локальные таблицы состава и снимка компонентов продажи с RESTRICT-ссылками.
Нет распознавания по бренду/названию, массового UPDATE и преобразования остатков.
Обычная карточка без конфигурации остаётся обычной. Доступность сборки вычисляется
отдельно как минимум целых частных stock/quantity активных компонентов.
Проведение раскрывает состав в физические движения внутри существующей транзакции,
сохраняя коммерческие строки. Отмена опирается на реальные движения.
Одноуровневые составы; self-reference, дубли, пустой состав и неположительные
количества запрещены. Ненулевой собственный остаток блокирует включение сборности.
Компоненты создаются существующим локальным механизмом, без отправки в Bitrix.

Production-остатки не исследовались и не изменялись. Конкретный список SKU для
конверсии не задан; примеры из задания не являются поручением конвертировать их.
Автоматическая конверсия любых существующих SKU не предусмотрена.

## Реализовано

- `app/bundle_migration.py`, дополнительный manifest, регистрация в
  `schema_migrations.py` и runtime DDL inventory: четыре новые таблицы
  `erp_product_bundles`, `erp_bundle_components`, `erp_local_components`,
  `erp_sale_component_snapshots`; индекс обратного поиска компонентов; два
  защитных триггера. Существующие таблицы и их данные не переписываются.
- `product_bundles.py`: явная настройка одного SKU, проверки состава, пакетная
  загрузка и отдельная доступность сборки. Количество компонента — целое >0.
- `sales_inventory.py`: физические списания компонентов в BEGIN IMMEDIATE,
  коммерческие позиции остаются в erp_sale_items; снимки названия, артикула и
  количества компонентов сохраняются независимо от текущего состава. Возврат
  использует снимок и доказанные движения; отмена — остаточный эффект журнала.
  Повторное проведение одного запроса/повторная отмена не меняют склад второй раз.
- `excel_product_catalog.py`, `bitrix_erp_product_sync.py`: компонент создаётся
  локально с нулевым stock. Отдельный маркер исключает его из Bitrix matching;
  триггер запрещает присоединять к Bitrix вручную. Конфигурация и движения
  остаются после sync. Приход/инвентаризация используют физические карточки.
- `receipt_inventory.py`: приход на коммерческий сборный SKU отклоняется с
  указанием оформить компоненты. Также нельзя назначить ему физический stock.
- `shared_catalog.py`, `catalog/application.py`, `catalog-combobox.js`: подбор
  продажи включает доступные сборные SKU и явно подписывает доступность сборки;
  обычные stock-фильтры сохраняют прежний смысл. Новые данные загружаются пакетом.
- `web.py`, `warehouse.html`, `product_bundle.html`: ссылка «Настроить состав»
  в карточке; страница `/app/products/<id>/bundle`, защищённое API GET/PUT,
  поиск и добавление компонентов, создание локального компонента. Общая таблица
  товаров не получает дополнительных запросов на каждую строку.

## Ограничения и доставка

Массовый интерфейс не добавлялся. Многоуровневые составы запрещены. Специальная
операция замены ремешка не принимает сборные SKU: они проводятся обычной продажей.
Ненулевой собственный stock и незавершённые физические списания блокируют перевод
SKU в сборный режим. Конкретные production SKU для преобразования не выбирались.

Браузер и агенты не использовались; визуальная проверка мобильного интерфейса
не выполнялась. Формы и API проверены Flask-клиентом, шаблоны и JS — синтаксически.
Внешняя Bitrix-сеть в тестах отключена; синхронизация проверена на фикстурах.

Существующая механика обычных товаров не была изменена по смыслу.
Существующие остатки не были автоматически преобразованы или обнулены.

Перед production обязательны успешные PR checks, штатный backup и rehearsal.
Для отката нужен согласованный backup БД и кода: предыдущая версия строго
проверяет схему и не принимает новые таблицы. После появления новых движений
нельзя молча восстанавливать старую БД с потерей этих движений.
Дополнительно актуализированы регрессии количества миграций и подписей выбора
товара; проверены 5 тестов структуры combobox, 9 коллекций и 3 runtime DDL gate.
На актуальном main повторно прошли 21 targeted test, 19 API товаров и 14 общего
каталога.

Commit, PR и итог deploy фиксируются в отчёте доставки, а не в данных каталога.
